Case studies

Two projects. Each one says what I built, one tradeoff I would defend, and how I know it works. Every claim links to code, a pull request or a document.

Joltrin: stop an AI agent from running a risky step too early

Open sourceI am a maintainer, not the sole author

Who owns what. The repo is in the SharedCode organization. I have admin rights, 407 of its 690 merged pull requests are mine, and the commits under my name cover the verification barrier: verify, the MCP server, the runbook loader, the Kubernetes gate and the docs for them. The B-tree storage engine underneath was written by Gerardo Recinto, who has most of the repo's history. I did not write the engine and I do not claim it.

User problem

An agent can propose a destructive action and report success from its own context. If the same agent also judges the action safe, both judgments fail for the same reason. The check has to sit outside the agent and confirm that the earlier steps, like a validated backup, were recorded.

Constraints

  • Someone should be able to try it without installing Go or running a server, so there is a browser demo and a no-Go installer. I moved those to the front of the README and the homepage: #737, #723, #729.
  • Teams already run agents and pipelines. Turning on a blocker against live traffic is risky, so there has to be a way to see its effect first.
  • The same check has to work in front of kubectl delete, under a cluster's own security rules.

What I built

  • Observe mode, SOP_MODE=observe: a dry run that runs everything and reports what would have been blocked. #762, code, docs. The demo uses it.
  • The Kubernetes admission gate: a webhook that refuses a delete until the runbook's earlier steps are recorded. Metrics, audit log and a deny-egress network policy in #544. Updates that strip the gate label or trace id are refused in #666. A read-only root filesystem in #766. Doc: KUBERNETES_GATE.md.
  • A script that reproduces the gate checks on a real kind cluster: #682, script.
  • Integration examples for a customer's stack: a Spring Boot agent service and a gate command that remembers allowed steps.
  • Honest docs: a comparison with Temporal and policy engines that says where Joltrin is weaker, and a security controls page with the status and limits of each control.

A tradeoff I would defend

The gate fails closed. I chose webhook failurePolicy: Fail over Ignore, so an outage cannot be used to skip the check. The cost is that a protected object cannot be deleted or updated while the gate is down. I limited the damage with a label selector, so only objects labeled joltrin.dev/gate are affected, and the doc says plainly that state is in memory on one replica. I would switch to fail-open only for a customer who values availability of those objects over the guarantee and has another control in front. It is a design choice recorded in the doc's "what it does not do" section. No customer asked for it.

Outcome and how I checked it

  • The gate was exercised against a real API server on kind with cert-manager, including a denied delete, a wrong-token 401, a 409 on out-of-order steps, and a delete that succeeds once the steps are recorded. The doc records this. I ran scripts/k8s-gate-e2e.sh on the pinned commit on 20 Nov 2026 and it ended 14 passed, 0 failed. It is not part of Joltrin's CI.
  • The customer demo drives the real server through observe, enforce, a restart and a rollback, with 15 checks.
  • The README quickstart runs as written. I ran go run .../examples/verify_barrier@latest from a clean directory and it printed the blocked drop, the backup, then the allowed drop.
  • Adoption: no usage numbers. I can show the install path, the browser demo and the first-run copy I changed. I cannot show who uses it.

meshdoctor: find the Istio mistakes that become 503s before you apply them

Personal projectSolo, lab scale

User problem

A platform team reviews Istio YAML by eye. Route weights that add up to 140, a subset used but never defined, or a client with TLS disabled against a strict namespace all look fine in review and show up as 503s after the apply.

Constraints

  • It has to run in CI with no cluster access and no credentials, because that is where a platform team can gate a pull request.
  • A reviewer who does not have Go should be able to paste YAML into a page and see the findings, so there is a WebAssembly build.
  • Every finding needs a fix line, or the on-call engineer is back to reading Envoy response flags.

What I built

  • A Go linter with 11 rules and three output formats, one of which is GitHub annotations for the pull request diff. rules.
  • A Jenkins shared-library step, meshGate, so the lint is one line in a pipeline.
  • Three runbooks for what happens after a 503: response flags, canary rollback and missing sidecar.
  • An end to end script that applies the manifests to a kind cluster with a Java checkout service that can fail on demand.

A tradeoff I would defend

The linter reads the files you give it and does not query the cluster. That lets it run before an apply with no credentials, which is where it is useful. It gives up the ability to see live state, so a rule that needs another resource only warns when that resource is not in the files. If a customer's real problem were drift between Git and the cluster, I would add a cluster-aware mode instead of pushing more rules into the file linter.

Outcome and how I checked it

  • From a clean clone, go test ./... passes, testdata/bad.yaml reports 4 errors and 9 warnings and exits 1, and testdata/good.yaml is clean and exits 0. I ran these for this page.
  • The repo's CI runs the tests and the kind end to end job. I did not rerun the end to end job for this page.
  • Limits the README states: the Terraform was validated but never applied to an AWS account, and the Jenkinsfile has not run on a build agent. It has no users I can point to.
