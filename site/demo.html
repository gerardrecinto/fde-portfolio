Customer demo: keep an agent away from production drops

A made-up team wants its AI maintenance agent to stop dropping production tables before a snapshot is verified. I take that from the discovery call to a deploy, break it on purpose, and recover.

Simulated The team, their requirements and their agent traces are invented. See requirements.md and traces.json.

Measured Every other line below is output from the real sop-mcp-server, built from Joltrin commit c994945. This page is rebuilt from a fresh run on every deploy.

The visit in eight steps

  1. Discovery. Five requirements from the call. The one that shapes the rollout: the nightly staging drill drops a table with no snapshot and must keep working.
  2. Integration. I write their existing step names into a runbook so their agent code does not change. My first draft misspells one state. The server refuses to load it because a step could never run.
  3. Dry run. Observe mode replays 14 traces, 55 steps, and blocks nothing. It reports 6 steps that would have been blocked. Three are real mistakes. Three are the staging drill, a false positive.
  4. Fix. The staging drill gets its own workflow. The agent change is one config line on their side. A second replay shows only the 3 real findings.
  5. Deploy. Enforce mode over HTTP with a bearer token, a decision log and Prometheus metrics. A wrong token gets 401. The agent's first drop is blocked and the reply names what to run first.
  6. Verify. The decision log and the metrics counter agree: 1 blocked, 5 allowed.
  7. Failure. The server restarts in the middle of a run. State is in memory, so the next drop is blocked even though the steps were done.
  8. Recovery. The agent replays the steps the block named and the drop runs. The rollback for enforcement itself is a restart in observe mode, and the log records it.

Run it yourself

git clone https://github.com/gerardrecinto/fde-portfolio && cd fde-portfolio
bash demo/run.sh

Needs Go 1.21 or newer and Python 3.9 or newer. Go downloads the version Joltrin needs by itself. The first run builds the server, which took 24 seconds on a GitHub runner and 76 on my laptop. Then it takes seconds. If you already have a sop-mcp-server, set SOP_MCP_SERVER=/path/to/it. The script exits 1 and says which check failed if anything is off, and ends with ALL 15 CHECKS PASSED when it works.

How to verify success

  • Exit code 0 and the last line ALL 15 CHECKS PASSED.
  • Step 5 rejects a wrong token with 401 and blocks the first drop with a reason.
  • Step 6 compares two independent records: the JSON decision log and the joltrin_steps_total metric.
  • Step 7 shows the failure is real: the same call that succeeded before the restart is blocked after it.
  • Read the checks in demo/fde_demo.py. They assert on the server's replies, not on strings I print.

What this does not show

  • No cluster. This runs the barrier as a local process. The Kubernetes admission gate is covered by Joltrin's own gate doc and scripts/k8s-gate-e2e.sh, not by this demo.
  • Pinned to a commit, not a release. Observe mode is on Joltrin's master branch but not in release v5.12.1. A customer should get a tagged release, so that is a gap to close before a real engagement.
  • Single tenant, one replica, state in memory. That is how Joltrin documents it. A restart makes the barrier stricter, never looser, which step 7 shows.
  • The agent is a script. It sends the steps in the traces. It is not an LLM, so this tests the barrier and the rollout, not agent behavior.
