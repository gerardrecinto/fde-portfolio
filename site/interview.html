Interview Q&A

Ten questions. Each starts with the answer I would say out loud in two sentences. The deep dive is there if you want it, and each answer links to the code or the demo behind it.

1 of 10 · Discovery

A customer says they want to stop their agent from breaking production. What do you do first?

I ask what happened last time and what has to keep working before I touch a tool. In my simulated demo the fact that shaped the whole rollout was that the nightly staging drill drops a table with no snapshot, and I only get that by asking.

Technical deep dive

I run the call around five questions: what failed and when, who is on call and what do they see, which steps does the agent actually call today, what already exists (ticketing, backups, a CI system), and what must not change. I write the answers down as requirements and send them back for a yes before I build.

In the demo those became five numbered requirements. Requirement 3, the staging drill, is the one that produced a false positive in the dry run. If I had skipped discovery I would have found it by blocking their drill.

2 of 10 · Scoping a proof of concept

How do you scope a proof of concept?

One workflow, one environment, and a success test the customer agrees to before I start, plus a written list of what the proof does not cover. My demo has that shape: one drop workflow, a local server, 15 checks, and a section that says what it does not show.

Technical deep dive

I timebox it, name what is stubbed, and decide up front what result means go and what means stop. The value of the list of exclusions is that nobody later mistakes a local process for a production deployment.

For Joltrin the exclusions are real: no cluster in the demo, one replica, state in memory, the demo is pinned to a commit because observe mode is not in a tagged release yet. I would close the release gap before a customer started, since a customer should not run from a commit hash.

3 of 10 · Integrating with the customer's stack

Their agent already has its own step names, and some of their services are Java. How do you integrate?

I fit the tool to their names and their language so their agent code does not change. In the demo the runbook uses their step names, and Joltrin has a Spring Boot example that sends plans through the barrier.

Technical deep dive

The runbook is a JSON file that maps their steps to the states they establish and require. sop-mcp-server check refuses a file where a step could never run, and it caught my own misspelled state in the demo. Agents talk to it over stdio, and services talk to it over HTTP with a bearer token.

The Spring Boot example is a service that submits a plan and gets a blocked or allowed result back. Before a real customer I would check the network path, the token handling and the timeouts, because those fail before the logic does.

Evidence: Their step names in a runbook · Spring Boot agent service, #764 · The example

4 of 10 · Production debugging

Something that worked is now failing in production. Walk me through it.

I find what changed, reproduce the failure with the smallest input I can, and fix it where the evidence points instead of where it looks likely. In my demo a restart made a drop that had worked get blocked, and the decision log and the reply named the missing state, which is how I confirmed it was lost trace state and not the rule.

Technical deep dive

I start with the record the system keeps, not with a theory. Joltrin's decision log has one JSON line per decision with the rule and the missing state, and the metrics counter gives the same count from a second source, so I can tell a real block from a bug.

For mesh traffic I use the order in meshdoctor's runbook: read the Envoy response flag first, because it separates no healthy upstream, a TLS mismatch and a timeout. I also break my own tools: in a field-kit commit I fixed a bisect helper that read the wrong output.

Evidence: Demo step 7 · 503 response flags runbook · Bisect fix

5 of 10 · Security

A customer's security team reviews your tool. What do you bring?

I bring what it cannot do next to what it can, starting with who holds the keys and what happens when it is down. For Joltrin's gate the commit token belongs to the backup job and not the agent, and an outage fails closed.

Technical deep dive

The Kubernetes gate doc lists its own limits: whoever holds the commit token can record a step, the trace id is only as trustworthy as who can write the annotation, and anyone who can edit the webhook configuration can remove the gate, so that needs RBAC.

I closed the gaps I could. Updates that remove the gate label or trace id are refused (#666), the container root filesystem is read-only (#766), and there is a deny-egress network policy with metrics and an audit log (#544). I note in the doc that the network policy was not tested, because that depends on the cluster's network plugin. For the install path, the script checks the release checksum and can verify build provenance.

Evidence: Gate doc, including what it does not do · #666 · #766 · #544 · Security controls page

6 of 10 · Rollout

How do you roll out something that can block production work?

Dry run first, enforce second, and only after the dry run's false positives are fixed. In the demo observe mode found three real mistakes and three false positives from the staging drill before anything was blocked.

Technical deep dive

I replay recent traces in observe mode and read every would-be block with the customer. Each one is either a real mistake the tool should catch or a gap in the runbook. In the demo I fixed the three false positives by giving the staging drill its own workflow, replayed again, and only then started enforcing.

The Kubernetes gate has the same idea as a flag: --warn-only allows everything and returns what would have been blocked as a warning. I would not turn enforcement on until the replay shows no false positives and the on-call person has seen the block message.

Evidence: Demo steps 3 to 5 · Observe mode, #762 · Operations doc

7 of 10 · Rollback

It is enforcing and blocking legitimate work at 2am. What is the rollback?

Restart it in observe mode, which stops blocking and keeps logging, then fix the runbook and replay before enforcing again. I rehearsed that in the demo, and the decision log records the rollback as observed.

Technical deep dive

Two caveats I would tell the customer. A restart forgets in-memory traces, so runs in flight have to replay their steps, which the demo shows in step 8. And the Kubernetes gate fails closed, so if the gate itself is down, protected objects cannot be deleted or updated.

The way out there is to restore the gate or, as a break-glass step, remove its webhook configuration, which needs the RBAC I said to restrict. I have not rehearsed that break-glass step in the demo, and I would before a real engagement. For the Joltrin website I added a rollback to the deploy workflow in #685.

Evidence: Demo steps 7 and 8 · Gate doc · Site deploy rollback, #685

8 of 10 · Adoption

How do you get the customer's team to actually use it?

I make the first run work in minutes and give the on-call person something readable at 2am. I changed Joltrin's README and homepage to lead with the no-Go install and a browser demo, and I would measure adoption by blocked-then-recovered runs in the log instead of installs.

Technical deep dive

The changes were small and specific: the browser demo and the no-Go install come before go run (#737, #723), and the page tells a new visitor what to ask their agent after installing (#729). A person who cannot get a first success in a few minutes does not read the docs.

For a customer I would use the block message as the training material, because it says what to run first. I have no usage numbers for Joltrin and I will not make any up. What I can show is the path I built and the signals I would watch.

Evidence: #737 · #723 · #729

9 of 10 · Core product or customer-specific

A customer asks for a feature. How do you decide whether it belongs in the core product?

If it changes the safety guarantee, or a second customer would need the same shape, it goes in core; if it is a name, a mapping or a threshold, it stays in their config. Observe mode went into core because every rollout needs a dry run, while the staging drill routing in my demo stays in the customer's runbook.

Technical deep dive

My checks, in order: does it change what the product guarantees, would a second customer need it, what does it cost me to maintain, and can it live outside the hot path as an adapter. Joltrin's NATS bridge is an example of the last one. It is optional, nothing imports it by default, and a failed publish can never change the barrier's answer.

I also write down what the product is not. The comparison doc says where Joltrin is weaker than Temporal or a policy engine, so a customer asks for the right tool instead of a feature that turns this one into something else.

Evidence: Observe mode in core, #762 · Customer routing in config · NATS adapter note · Comparison doc, #715

10 of 10 · Honesty

What is the weakest part of your evidence?

I have not deployed either project for a paying customer, so I show a simulated visit and label it as simulated. What I can show is real code, real checks and the limits written next to each claim.

Technical deep dive

The gaps, plainly: no customer and no usage numbers, a demo pinned to a commit because observe mode is not in a tagged release, no cluster in the demo, meshdoctor's Terraform validated but never applied, and its Jenkinsfile never run on a build agent.

The work I would do first in a real engagement is the part I could not do alone here: get a customer's real traces, ask for a tagged release, and run the gate in their cluster.
